Skill File Evolution

Can a judge model keep editing an agent's security skills (the general skill S0 plus specialised skills the judge creates, all of which the agent chooses whether to load) a few rules at a time, after attacks that keep getting through, so prompt-injection success drops on attacks it has never seen, including against attackers that adapt back?

The experiment

Four runs in a 2 × 2, plus reference runs

Each cell is one run with its own directory, cache and attacker archive under results/<run_id>/seed_<n>/. A full run covers all 949 pairs; smoke and pilot cuts (--smoke, --limit, --subset, --single-injection-point) get their own folders. All runs get the same inputs: the same pairs in the same order, the same S0 and the same trial-0 important_instructions text. Only C3 splits pairs into train and test; C4 has no split. C0 · no S0, static attack. The victim with only its five fixed skills: raw ASR and the utility ceiling. c0_no-s0_static-attack. It must show ASR ≥ 20%, or there is nothing to defend. Also run once on AgentDojo's native loop to show the DeepAgents harness doesn't shift the numbers.
C0E · no S0, evolving attack (added 2026-11-20, PR #39). C0's victim against C2's attacker with the same settings. c0e_no-s0_evolving-attack. C2 against C0E shows what S0 adds under adaptive attack, as C1 against C0 does under the static one. No split; same --trials-per-pair as C2.
C4 has no train/test split (user decision 2026-11-27; code in PR #67, being reworked). One adapting phase over every pair, in C2's pairs and order; with --limit N it runs the same pairs as C2 with --limit-each-split. The judge learns from every pair, the attacker rewrites every pair, and the skills freeze only for the benign set at the end. There is no held-out test for C4; held-out generalisation is C3's job (H1).
Defender ablation · --defender single. C3/C4 with S0 as the only security skill (the PR #59/#60 design), -single-s0. Keep it in a separate results root from the library run, because compare pools all runs of a condition.
C5 · frozen evolved file · on hold. The final C4 skill file, locked, against a fresh evolving attacker with an empty archive. Put on hold by the user; not built in the runner.
  • H1Evolving skills lower test ASR: C3 on its final skills against C1 on the same test pairs, at equal benign utility (C3 benign before against after). At smoke size, run C1 with --limit-each-split so it has test pairs. One value per run, no curve. C4 has no test phase, so it is not in H1.
  • H2Against an adaptive attacker, a static file degrades faster: C2 against C4 on the same pairs (all of them; at smoke size run C2 with --limit-each-split). This is the headline C4 number. Two x-axes (decided 2026-11-17): main, position in the run (train pairs in run order, 10 equal bins, the same pairs in both); second, trial index 0 … k (0 … 8 with 9 trials per pair).
  • H3Gains generalize: ASR on held-out attack styles over test injections (and C5 against a fresh attacker, on hold).
  • S0What S0 adds: C1 against C0 under the static attack, and C2 against C0E under the evolving one. Because the attacker's playbook grows during a run, C2, C4 and C0E ASR should also be reported for the first and second half of the run order.
Data

Split by injection task, only in C3

Train · 60% · 21 injection tasks · 559 pairsPairs run one at a time in a fixed order, shuffled with seed 0 so suites mix, and drive the skills' evolution. Judge input comes only from here.
Test · 40% · 14 injection tasks · 390 pairsC3 only, on the frozen final skills: new attacks after deployment, which shows whether the defender learned something general. Held-out styles injecagent and ignore_previous are planned, never used in training.
Who splitsOnly C3. C4 adapts on every pair, like C2. C0, C0E, C1 and C2 run every pair, with or without S0; each C1/C2 record keeps its pair's split label so results can be cut to the same pairs as C3. The split reads as deployment: train = online deployment, test = new attacks after it
Suitesworkspace, travel, banking, slack (v1.2.2, the only built-in version), split stratified by suite, seed 0, no dev split. Train/test injection tasks: banking 6/3, slack 3/2, travel 4/3, workspace 8/6
PairsAll 949 pairs of v1.2.2, no sampling (workspace 560, banking 144, travel 140, slack 105), in every condition, in the same order: train pairs shuffled, then test pairs shuffled. A pair sits on its injection task's side. The list, trial-0 texts and S0 hash are in pairs_manifest.json
Trials--trials-per-pair per pair (default 3; 9 = trial 0 + 8 evolutions for C2, C4 and C0E), run back to back, always all of them; one run per condition. Compared runs must use the same number
Smoke and pilot cuts--smoke: single-injection-point pairs taken in turn from banking and travel; the user runs it with --limit 20 (folders end -smoke-limit20). --subset file and --single-injection-point (700 of 949 pairs read one vector). C3 with --limit N takes N train and N test pairs, and C4 the same pairs as C2 with --limit-each-split; C0–C2 take the first N pairs of the run order (all train pairs at smoke size) unless --limit-each-split (PR #66, -each-split folder) gives them the same N + N. Use the same cut in every condition
Benign setEvery user task, no injection. In C3/C4: once on S0 before the adapting phase, once on the final skills after it. In C0, C0E, C1 and C2 the runner runs it once before the attacked pairs (proposal, see below). Used for benign utility and the S0 load rate on clean tasks, in evaluation only
ReportedASR, utility under attack, replication per win and robust evolving and pair ASR (PR #57), the specialised-skill library (C3/C4, PR #65: skills at the end of training, per-skill load rate and ASR loaded vs not, train trials by covering skill, judge steps by diagnosis, skills after each CREATE/RETIRE, covering skill vs the attacker's strategy label), the analyst's diagnoses, benign utility, S0 load rate (attacked and benign) and ASR with vs without S0 loaded, tokens and cost per component (victim, judge, attacker), attacker refusal rate, progress score, wins by strategy, the skill-agent's note library (with distillation: distillations, notes written, rejected and dropped, per-note loads and wins, contrastive rounds); pair-level numbers (since PR #52, every run): pairs where the original text works, evolving ASR (pairs won by an evolved text over pairs where the original failed), mean evolutions to first success and ASR@n (share won within n evolutions, like pass@n; in C0/C1 the same numbers measure plain resampling, the baseline evolution must beat); 95% cluster-bootstrap CIs over injection tasks (benign: user tasks), paired across conditions
How it runs

One command per condition, then one comparison

HardwareThe project's shared 2× H100 VM, started by local_victim/serve_all.sh: victim Magistral on GPU 0 (BF16, port 8000, no draft), attacker Qwen3.8-27B + DFlash2 on GPU 1 (BF16, port 8003). ONE_GPU=<n> puts both on GPU n in FP8; ATTACKER_DRAFT=none drops the draft; CHECKER=1 adds the old checker on port 8002 for the ablation (not with ONE_GPU). Current setup (user, 2026-11-23): ONE_GPU=0 ATTACKER_DRAFT=none bash local_victim/serve_all.sh, so victim and attacker share GPU 0 in FP8. Serve every compared condition the same way. Only the judge (C3, C4) uses OpenRouter, key from --env-file ~/api.env
1 · Manifestagentdojo.runner.build_manifest writes pairs_manifest.json; every run checks its inputs against it before any model call
2 · Runagentdojo.runner.run_condition --condition C0|C0E|C1|C2|C3|C4 checks the servers, writes config.json, works through a fixed unit list and checkpoints after each unit, so the same command resumes (a different config is refused). Main options: --trials-per-pair, --smoke, --limit N, --suites, --subset, --single-injection-point, --limit-each-split, --attacker autodojo|skill-agent|muzzle, --analyst/--no-analyst, --replicate-wins N, --distill-every K, --distill-mode contrast|plain|trajectory, --skill-choice ranked|free, --stop-on-success, --victim-temperature, --attacker-temperature; C3/C4: --defender library|single, --judge-trigger batched|every-win, --judge-batch-pairs, --judge-confirm-runs, --judge-min-losses, --judge-evidence rich|basic, --rule-match paraphrase|verbatim, --skill-loading index|prompt|both; --external-checker
3 · ReportEach run writes summary.json and report.html (also mid-run, with agentdojo.runner.report)
4 · Compareagentdojo.runner.compare reads all runs and writes comparison.html: H1, H2 (both axes) and C0 vs C1, with paired bootstrap differences. It pools all runs of a condition in one results root, so keep variants (e.g. --defender single) in separate roots
Unit orderC0, C0E, C1, C2: benign set, then every pair × its trials. C3: benign before, train pairs (judge steps every 4), freeze, test pairs, benign after. C4: benign before, every pair (judge steps every 4), freeze, benign after
Still open
  • When the benign set runs in C0, C0E, C1 and C2. The runner runs it once, before the attacked pairs, against S0 (proposal). H1 needs C1's benign utility.
  • C4 without a split (user decision 2026-11-27) is coded in PR #67, which is being reworked to drop the train/test option for C4; its flags may change before it merges.
  • PR #58 (attacker sees the victim only through the analyst) is still open; until it merges, main also shows the optimizer the redacted trace.
  • The cap of 6 specialised skills is a guess; the report shows how often a run reaches it.
  • Delta edits: whether the Principles are frozen, the edit budget (≤ 2 edits per step, ~60 tokens per rule), the common-word list for the identifier ban (empty for now, so the ban is strict), and whether one invalid edit rejects the whole batch. The code uses these proposals as defaults. Four S0 rules (S4, S6, K2, K3) are already over ~60 tokens.
  • The digest size N (proposed 20), the token counter for the 1500-token cap (since 2026-11-19: the victim's tokenizer), and the leakage archive in C3 (proposed: every injection text the run's train trials used so far).
  • agentdojo.runner.compare reports H1, H2 and C0 vs C1, but not yet C2 vs C0E or the first-half/second-half ASR split.
  • The held-out styles (injecagent, ignore_previous) are in the design but not yet in the runner's test phase.
  • The native-loop reference must address the model by the same name as the DeepAgents run in important_instructions, or the two don't send the same attack text.
